Testes e experimentos

10 experimentos, comando → resultado real → o que isso prova

6 cobrem o ciclo de vida completo de uma NF (results/experiments.csv); os outros 4 cobrem monitoramento, orquestração contínua, configuração e uma primeira função de Non-RT RIC — a mesma exigência de evidência real vale para todos.

EXP‑01Provisioning
Instantiate — 3 CNFs do zero
20,4 s·kpt live apply via Porch▸
Comando
bash lab/nephio/deploy-cnfs-via-porch.sh
Resultado real
porchctl rpkg copy/push/propose/approve ... kpt live apply --prune-propagation-policy=Foreground apply result: 10 attempted, 10 successful, 0 skipped, 0 failed oran-cu/du/core → 1/1 Running

Prova: as NFs chegam ao cluster por um pacote publicado no Porch (Draft→Proposed→Published), não por kubectl apply direto — o mecanismo real de entrega do Nephio.

O que este laboratório não é

Consistente com a regra deste trabalho: nunca declarar que algo "funciona" só porque uma CRD existe. Estas são as fronteiras reais, sem retoque.

✕NFs simuladas (FastAPI), não implementações O-RAN reais — sem F1/E1/E2, sem plano de usuário/controle.
✕O-Cloud = cluster kind via CAPD (Docker), não OpenStack/bare-metal/cloud real; sem inventário O2 de hardware.
✕FOCOM roda no mesmo cluster do management — a federação com um SMO externo nunca foi exercitada.
✕o-cloud-1 não sobrevive a um restart abrupto da VM do WSL2 sem re-provisionamento (CAPD + cgroup v2).
✕provisioningState: fulfilled é PoC de rascunho O-RAN WG6 — oCloudNodeClusterId é um UUID local, não um id de inventário O2 real.
✕config-bridge cobre só oran-du/cell_id — generalizável, mas não aplicado às demais NFs/campos.
✕xApp deliberadamente não simulado — exigiria um Near-RT RIC + protocolo E2 reais, que este laboratório não implementa (não existe "A2" na especificação O-RAN; as interfaces reais são A1 e E2).
✕rApp aplica a decisão direto via API do Kubernetes — não publica uma policy A1 para um Near-RT RIC, que não existe neste laboratório.
